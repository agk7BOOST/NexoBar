# Frontend transversal y composición de App

React 19 + TypeScript estricto + Vite 8. Leer únicamente la documentación de la superficie afectada; las migraciones pertenecen al backend.

- `App` coordina `CatalogPanel`, `OrderWorkflow` y `OrderLookup`; las responsabilidades de catálogo/Price Change, Pedido activo/Composición y consulta están separadas. Un `Order` consultado puede retomarse para una Composición posterior mientras su Estado lo permita; Frozen/Closed impide continuar ordinariamente.
- `GeneralConfigurationPanel` se monta sólo si la proyección autoritativa actual incluye `GeneralConfiguration`. El chequeo cliente limita visibilidad y navegación, no autoriza endpoints: cada read y comando continúa bajo la autoridad del backend. Tras una mutación propia de Functional Responsibilities, `App` reconcilia `GET /api/identity-sessions/current`; una auto-revocación exitosa retira la superficie sólo desde ese snapshot.
- La administración web de Identity reconcilia cada comando desde su respuesta backend. No confirma Estado optimista; una incertidumbre conserva la intención y su `Idempotency-Key` para reintento explícito. La administración de Preparation enablement es separada de `Preparation` y resuelve los nombres operacionales mediante el read de `OperationalConfiguration` autorizado por `GeneralConfiguration`.
- Un secret de LocalCredential sólo existe transitoriamente en el formulario. Reemplazar la credencial propia reconoce primero el POST exitoso y después retorna a login, porque el backend revoca todas las Sessions objetivo; una nueva sesión debe recuperar la proyección actual antes de volver a montar la superficie.
- La carga anónima actual de Catalog es deuda de seguridad temporal. S9 exige que no haya fetch anónimo de administración, que `CatalogPanel` se monte sólo con `CatalogConfiguration`, y que Composición obtenga su read operacional de Product independientemente de esa responsabilidad. El lookup de Preparation Responsibility se carga sólo para configuración de Catalog. Esto no diseña nuevas pantallas.
- Los recursos se refrescan desde la autoridad: Price Change recarga `Catalog` y las Confirmaciones recargan el `Order`. El cliente no compone manualmente la Historia.
- En reads sensibles a SSE, una invalidación sólo marca stale y provoca GET autoritativo; no muta State de negocio desde el payload. El App mantiene una conexión por Session con el snapshot de scopes actual, refresca al abrir/reconectar y usa fencing por generación por clave de read para que una respuesta anterior no sobrescriba un refresh más nuevo. El vertical de destino de Preparation está implementado; los demás scopes permanecen diferidos. Los detalles transversales están en [SSE y frescura multiusuario](../architecture/sse-and-freshness.md).
