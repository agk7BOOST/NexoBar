# Frontend transversal y composición de App

React 19 + TypeScript estricto + Vite 8. Leer únicamente la documentación de la superficie afectada; las migraciones pertenecen al backend.

- `App` presenta un App Shell con navegación por espacios derivada de `CurrentIdentity.responsibilities`: Pedidos, Preparación, Productos, Inventario y Configuración. Los paneles autorizados permanecen montados bajo `hidden` al cambiar de espacio para conservar selección e intenciones en memoria. `OperationalIntervention` sin `Preparation` presenta su acceso puntual como «Intervención en preparación»; no concede cola ni acciones generales de Preparation. El backend conserva la autorización de cada read y comando.
- `App` coordina `CatalogPanel`, `OrderWorkflow` y `OrderLookup`; las responsabilidades de catálogo/Price Change, Pedido activo/Composición y consulta están separadas. Un `Order` consultado puede retomarse para una Composición posterior mientras su Estado lo permita; Frozen/Closed impide continuar ordinariamente.
- `GeneralConfigurationPanel` se monta sólo si la proyección autoritativa actual incluye `GeneralConfiguration`. El chequeo cliente limita visibilidad y navegación, no autoriza endpoints: cada read y comando continúa bajo la autoridad del backend. Tras una mutación propia de Functional Responsibilities, `App` reconcilia `GET /api/identity-sessions/current`; una auto-revocación exitosa retira la superficie sólo desde ese snapshot.
- GeneralConfiguration lista y crea Contextos configurados mediante su superficie administrativa; `OrderOperationsAndBasicClosure` selecciona Context en First Confirmation y puede cambiarlo durante la operación del Order. La UI presenta `operationalName`, oculta el UUID técnico y no añade controles de lifecycle. Preparation consume el Context actual del Order para coordinación. Véanse [OperationalConfiguration](../operational-configuration/README.md#context-configurado--mvp-fc-ctx-closed) y [workflow de OrderOperations](../order-operations/frontend.md#context-configurado-y-context-change--mvp-fc-ctx).
- La administración web de Identity reconcilia cada comando desde su respuesta backend. No confirma Estado optimista; una incertidumbre conserva la intención y su `Idempotency-Key` para reintento explícito. En `GeneralConfigurationPanel`, la administración de Preparation enablement es separada de `Preparation`, y el mismo panel lista y crea Preparation Responsibilities por nombre operacional mediante el read autorizado de `OperationalConfiguration`. Crear ese destino no otorga `Preparation` ni un enablement.
- Un secret de LocalCredential sólo existe transitoriamente en el formulario. Reemplazar la credencial propia reconoce primero el POST exitoso y después retorna a login, porque el backend revoca todas las Sessions objetivo; una nueva sesión debe recuperar la proyección actual antes de volver a montar la superficie.
- Identity Delete se ofrece sólo en `GeneralConfigurationPanel`, con confirmación explícita distinta de Desactivar. La UI no decide la elegibilidad histórica; interpreta el conflicto funcional y el de última vía GC sin desactivar automáticamente. Tras Delete ajeno recarga el listado; tras auto-delete usa la reconciliación ordinaria de Session y vuelve al estado sin autenticación.
- La carga anónima actual de Catalog es deuda de seguridad temporal. S9 exige que no haya fetch anónimo de administración, que `CatalogPanel` se monte sólo con `CatalogConfiguration`, y que Composición obtenga su read operacional de Product independientemente de esa responsabilidad. El editor dedicado de Preparation del `CatalogPanel` carga el lookup de destinos de Catalog sólo para esa configuración; no usa las APIs administrativas de `OperationalConfiguration` ni exige `Preparation` o un enablement.
- Product Availability Intervention es una superficie separada de `CatalogPanel`. Se monta únicamente con `OperationalIntervention`, usa `GET /api/catalog/availability-administration-products` y el comando específico de Availability, y no requiere `CatalogConfiguration` ni `OrderOperationsAndBasicClosure`. El read devuelve sólo Products activos con id, nombre operacional y Availability; `GET /api/catalog/operational-products` continúa reservado a Composición. La UI recarga el read autoritativo después de mutar, refresca ante conflicto stale y conserva la intención exacta para reintento explícito incierto.
- Los recursos se refrescan desde la autoridad: Price Change recarga `Catalog` y las Confirmaciones recargan el `Order`. El cliente no compone manualmente la Historia.
- En reads sensibles a SSE, una invalidación sólo marca stale y provoca GET autoritativo; no muta State de negocio desde el payload. El App mantiene una conexión por Session con el snapshot de scopes actual, refresca al abrir/reconectar y usa fencing por generación por clave de read para que una respuesta anterior no sobrescriba un refresh más nuevo. El vertical de destino de Preparation está implementado; los demás scopes permanecen diferidos. Los detalles transversales están en [SSE y frescura multiusuario](../architecture/sse-and-freshness.md).
